# Stage123 통합 구조 진단 및 재정리 방향

내 판단으로는, 문제 인식이 거의 정확해. 다만 핵심은 “각 stage 구현이 잘못됐다”기보다, stage를 팀의 업무 분할 기준으로 삼으면서 시스템 모듈 경계까지 대신하게 된 것이야.

현재는 전부 갈아엎을 상황은 아니고, “계약과 책임을 다시 고정하는 작업”이 먼저야.

## 자료와 실제 코드에서 확인된 현재 상태

문서상 공식 실행 경로는 다음과 같아.

```text
scripts/run_e2e.py
→ integration/composition.py
→ stage1
→ stage2
→ stage3
```

이 구조는 [stage123-integrated/readme.md](C:/projects/dis-164/stage123-integrated/readme.md)와 [INTEGRATION_REPORT.md](C:/projects/dis-164/stage123-integrated/docs/INTEGRATION_REPORT.md)에 명시되어 있어.

테스트는 통합 11개, Stage3 65개가 통과하지만, 실제 대회 전체 코퍼스 기반 검증은 아직 안 됐어. 기본 fixture도 70개 기업 전체가 아니라 삼성전자 중심 21개 chunk야. 따라서 현재 테스트는 “구조와 계약이 깨지지 않는가”는 확인하지만, “대회 질의에 충분히 잘 답하는가”까지 보장하지 않아.

## 1. Stage를 나눈 것 자체는 문제 없어

Stage1 → Stage2 → Stage3라는 흐름은 자연스러워.

문제는 각 Stage가 실제로 다음처럼 겹친다는 점이야.

- Stage1: 질의 이해와 라우팅
- Stage2: LLM이 검색어를 만들고 Tool을 선택하며 재검색
- Stage3: 다시 질문 유형을 키워드로 판단하고 계산·비교·이벤트 연결
- Stage3: 답변 작성과 검증

특히 Stage3의 `analysis_targets()`와 `build_calculation_plan()`이 Stage1의 `intent`를 받으면서도 질문 원문을 다시 검사해 계산·비교 여부를 판단하고 있어.

즉 문서에는 “Stage1이 질문 분류를 담당한다”고 되어 있지만, 실제 코드에는 Stage3에도 또 다른 분류기가 있어. 이것이 팀원마다 같은 질문을 다르게 해석하는 원인이 될 수 있어.

## 2. 인터페이스가 없는 게 아니라, 여러 인터페이스가 동시에 있어

현재 코드에는 다음 계약들이 이미 존재해.

- Stage1: `Intent`, `ManifestFilter`
- Stage2: `SearchRequest`, `Stage2SearchResult`
- Stage3: `Stage2Bundle`, `Stage3Fact`, `Stage3Result`

하지만 실제 통합 경계에서는 `dict[str, Any]`로 넘기고, 각 단계가 다시 해석해.

예를 들어 [stage2_agent.py](C:/projects/dis-164/stage123-integrated/stage2/stage2_agent.py)는 `corps`와 `manifest_filter`를 다시 조합해서 검색 필터를 만들고, [stage2 어댑터](C:/projects/dis-164/stage123-integrated/stage3/adapters/stage2.py)는 `id`, `doc_id`, `chunk_id`, `text`, `content`, `page_content` 등 여러 형태를 허용해.

이건 통합 초기에는 유용하지만, 팀 합의 관점에서는 위험해. 서로 다른 결과물을 “어댑터가 어떻게든 맞춰주는” 구조가 되기 때문이야.

따라서 현재 문제는:

> 인터페이스가 없음
> 이 아니라
> 인터페이스가 여러 개이고, 어느 것이 진짜 표준인지 팀이 합의하지 않음

에 가까워.

## 3. 현재 구현은 처음 세운 설계와도 조금 다르다

처음 생각한 “작은 모델 → 마스터 모델” 구조가 현재 실제 실행 경로에는 그대로 구현되어 있지 않아.

현재 설정상:

- Stage1 LLM은 기본적으로 꺼져 있음
- Stage2만 `ChatClovaX`를 호출함
- Stage3의 `AnswerWriter`에는 HyperCLOVA X client가 주입되지 않아 deterministic template이 기본 사용됨

즉 현재는 사실상:

```text
규칙 기반 Stage1
→ Stage2 검색용 HyperCLOVA X
→ 규칙 기반 Fact/계산/비교
→ 템플릿 답변
```

에 가까워.

또한 `app/agent`는 legacy 경로이고, 루트의 [app.py](C:/projects/dis-164/app.py)는 여전히 `classic`, `langgraph`, `agentic` backend를 선택해. `stage123-integrated`의 공식 경로와 실제 루트 API 경로도 아직 완전히 하나로 합쳐진 상태는 아니야. 게다가 통합 폴더의 Dockerfile은 현재 비어 있어.

## 4. 예외 처리는 지금 설계하는 게 맞아

다만 모든 예외를 지금 다 구현하자는 뜻은 아니야.

지금 정해야 하는 것은 내부 예외의 세부 종류가 아니라, 각 경계에서의 실패 계약이야.

예를 들면:

```text
Stage1 route
- ok
- need_clarify
- unanswerable
- unsafe

Stage2 retrieval status
- ok
- not_found
- provider_error
- schema_error

Stage3 analysis status
- success
- insufficient_evidence
- invalid_alignment
- unsupported_operation
- error
```

그리고 반드시 구분해야 해.

- 검색 결과가 없음
- 검색 API가 실패함
- 문서는 찾았지만 숫자 근거가 부족함
- 숫자는 있지만 기간·단위·연결/별도 기준이 안 맞음
- 답변 생성은 됐지만 검증에 실패함

현재도 `status`, `warnings`, `trace`가 있지만 각 단계의 의미가 완전히 통일되어 있지는 않아. 그러므로 예외 처리는 “나중에 붙이는 기능”이 아니라 인터페이스의 일부로 지금 정하는 것이 맞아.

## 내가 추천하는 재정리 방식

Stage라는 이름은 유지해도 되지만, 실제 계약은 다음 네 가지로 단순화하는 게 좋아.

```text
Question
  ↓
QueryPlan
  ↓
EvidenceBundle
  ↓
AnalysisResult
  ↓
SubmissionResponse
```

각 책임은 이렇게 고정하면 돼.

- Stage1은 `QueryPlan`만 만든다.
  - 기업
  - 기간
  - 공시 범위
  - 지표
  - 계산 연산
  - 연결/별도
  - 정정공시 정책
  - route

- Stage2는 `QueryPlan`을 받아 `EvidenceBundle`만 반환한다.
  - 검색
  - rerank
  - 재검색
  - stable document ID
  - 본문
  - metadata
  - evidence span

- Stage3는 `QueryPlan + EvidenceBundle`만 받아 `AnalysisResult`를 만든다.
  - Fact 추출
  - 계산
  - 비교
  - 계약·정정 연결
  - 답변 작성
  - 인용

- 검증은 지금부터 최소한의 계약 검증만 둔다.
  - 필수 필드
  - 상태값
  - 문서 ID 존재
  - 계산 입력과 결과
  - citation 연결

가장 중요한 규칙은 이것이야.

> Stage2와 Stage3는 질문을 다시 분류하지 않는다.
> Stage1의 QueryPlan을 신뢰하고, 잘못됐다고 판단되면 명시적인 오류를 반환한다.

## 팀이 지금 당장 할 순서

1. `QueryPlan`, `EvidenceBundle`, `AnalysisResult`의 필드를 팀이 먼저 합의한다.
2. 각 단계의 입력·출력 타입을 하나로 고정한다.
3. `dict`와 alias 처리는 통합 경계의 adapter 안에서만 허용한다.
4. Stage3의 키워드 기반 재분류를 제거하고 Stage1의 operation을 사용한다.
5. 삼성전자 단일 수치 조회 하나만 완전한 golden path로 만든다.
6. 그다음 비교 → 계산 → 정정/계약 연결 순서로 기능을 추가한다.
7. 마지막에 전체 corpus와 실제 배포 환경을 검증한다.

결론적으로, 지금 필요한 것은 새로운 RAG 기술이나 더 복잡한 Agent가 아니야.

현재 통합본은 충분히 살릴 수 있고, 먼저 해야 할 일은 [integration/composition.py](C:/projects/dis-164/stage123-integrated/integration/composition.py)를 중심으로 각 단계의 책임과 데이터 계약을 다시 고정하는 것이야.
